# Integration Cookbook

These recipes build on the complete request in the [API reference](/docs/api-reference). Convey is pre-release; run integrations against your own deployment and consult the [V1 contract candidate](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/operations/v1-contracts.md) for current limits.

## Schedule a message

Add `scheduledAt` and optionally `expiresAt` to a valid send body:

```json
{
  "scheduledAt": "2027-01-10T09:00:00.000Z",
  "expiresAt": "2027-01-10T10:00:00.000Z"
}
```

These fields are additions to the full message request. Use future ISO timestamps. Explicit future scheduling returns `state: "scheduled"` plus `scheduledAt`; acceptance does not promise delivery at an exact time.

## Fall back from WhatsApp to SMS

Provide both `recipients.whatsapp` and `recipients.phone`. Set the initial `channels` array to WhatsApp, then include the SMS content in the fallback rule:

```json
{
  "recipients": { "whatsapp": "+14155552671", "phone": "+14155552671" },
  "channels": [{
    "channel": "whatsapp",
    "content": { "template": "order_confirmed", "language": "en", "variables": { "orderId": "10928" } }
  }],
  "fallback": {
    "rules": [{
      "when": { "channel": "whatsapp", "event": "failed" },
      "send": [{ "channel": "sms", "content": { "text": "Order 10928 is confirmed." } }]
    }]
  }
}
```

Merge this fragment into a complete send request. The WhatsApp template and provider configuration must exist. The provider-send worker queues this `failed` rule after final failure. Provider choice belongs to configured routing. See the [fallback state machine](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/fallback-state-machine.md) for processing details.

## Handle bulk results

Split input into chunks of at most 500 complete requests, each with a distinct idempotency key. Submit `{ "messages": [...] }` to `/v1/messages/bulk`. A `202` response is the batch envelope: check each item's `index`, `statusCode`, and `body`. Retry the same logical message with the same body/key; do not generate a new key simply because the connection failed.

## Exercise sandbox scope

Use a sandbox-scoped key or send `X-Convey-Sandbox: true` with an authorized key. The server derives sandbox selection from authentication/headers. Inspect recent records with `GET /v1/sandbox/messages`. Shared configuration resources have separate access restrictions, so a sandbox key cannot configure production providers or customer subscriptions.

## Preview a failed-message correction

First inspect a failed message with `/v1/dlq` and its timeline. A mutated replay can change recipients, channels, or metadata:

```bash
curl http://localhost:3000/v1/dlq/replay-mutated \
  -H "Authorization: Bearer $CONVEY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "messageIds": ["msg_01J0N7C0W7X2R6S8V9Q9B1E4G3"],
    "dryRun": true,
    "mutations": {
      "recipients": { "email": "corrected@example.com" },
      "metadata": { "remediationReason": "Recipient corrected their email" }
    }
  }'
```

Review `dryRunResults`; a dry run reports payload changes without dispatching or testing an actual provider route. After reviewing the changes, use `dryRun: false` to replay eligible failures. An intentional replay is another execution and can incur another provider charge. Ordinary replay uses `POST /v1/dlq/replay` with only `messageIds`.

## Receive delivery events

Use the [webhook recipe](/docs/webhooks) to create a customer subscription and verify the raw signed body. The server sends `{ event, timestamp, data }`. Make application updates safe to repeat; receipts can arrive after polling has already observed a newer state.
