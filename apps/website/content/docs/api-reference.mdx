# REST API Reference

Convey is pre-release. This reference describes the current server implementation; acceptance is asynchronous and does not mean delivery. The [repository API reference](https://github.com/hamidrezakks/convey/blob/main/docs/api.md) covers additional routes, and the [V1 contract candidate](https://github.com/hamidrezakks/convey/blob/main/docs/operations/v1-contracts.md) records the current guarantees and limits.

## Base URL and authentication

The local server uses `http://localhost:3000` by default. Use your own deployment URL in production. The SDK base URL is the server origin; resource methods add `/v1` themselves. Interactive API documentation is served at `/swagger`.

Tenant requests use `Authorization: Bearer <api-key>`. Stored credentials determine tenant, team, role, and sandbox scope. Production requires authentication; a local development bypass is available only when configured. Use a team that belongs to your key. `traceparent` is optional.

Idempotency is a required **body field** for message sends. Reuse the same key and payload for retries within the configured retention window (24 hours by default). A conflicting payload returns `409`; retention expiry can permit new work.

## Send a message

`POST /v1/messages`

```bash
curl http://localhost:3000/v1/messages \
  -H "Authorization: Bearer $CONVEY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "idempotencyKey": "order-10928-confirmation",
    "userId": "customer-42",
    "team": "payments",
    "category": "transactional",
    "country": "US",
    "priority": "transactional",
    "recipients": { "email": "customer@example.com" },
    "channels": [{
      "channel": "email",
      "content": { "subject": "Order confirmed", "text": "Your order is confirmed." }
    }]
  }'
```

Required fields are `idempotencyKey`, `userId`, `team`, `category`, a two-character `country`, `recipients`, and a nonempty `channels` array. Priority defaults to `normal`; wire values are `critical`, `transactional`, `normal`, and `marketing`.

| Channel | Recipient field | Content |
| :--- | :--- | :--- |
| `email` | `email` | Required `subject`; optional `html`, `text`, or `render` |
| `sms` | `phone` | `text` |
| `whatsapp` | `whatsapp` | `text` or provider template fields |
| `telegram` | `telegramChatId` | `text`; optional `parseMode` |
| `slack` | `slack.channelId` | `text`; optional `blocks` |
| `fcm` | `fcmTokens` | `title`, `body`; optional string-valued `data` |
| `apns` | `apnsTokens` | `title`, `body`; optional `badge`, `sound`, `data` |

Provider configuration and capability coverage vary by channel. See [providers](/docs/providers) before choosing a route.

A successful immediate acceptance returns `202`:

```json
{
  "messageId": "msg_01J0N7C0W7X2R6S8V9Q9B1E4G3",
  "state": "accepted",
  "createdAt": "2026-10-10T12:00:00.000Z"
}
```

`scheduledAt` and `expiresAt` accept ISO timestamps. Explicitly future-scheduled messages return `state: "scheduled"` and `scheduledAt`. Sandbox selection comes from authenticated scope or the `X-Convey-Sandbox: true` header, rather than a message body field.

## Bulk sends

`POST /v1/messages/bulk` accepts `{ "messages": [...] }` with **1–500 complete send requests**. Every item needs its own idempotency key. The HTTP `202` response includes per-item outcomes; inspect `statusCode` and `body` for each item.

```json
{
  "total": 1,
  "items": [{
    "index": 0,
    "statusCode": 202,
    "body": {
      "messageId": "msg_01J0N7C0W7X2R6S8V9Q9B1E4G3",
      "state": "accepted",
      "createdAt": "2026-10-10T12:00:00.000Z"
    }
  }]
}
```

## Status and related routes

| Method and route | Purpose |
| :--- | :--- |
| `GET /v1/messages/:messageId` | Aggregate `state` and per-channel state, provider attempt counts, and receipt timestamps |
| `GET /v1/messages/:messageId?include=timeline` | Status with chronological events |
| `GET /v1/messages/:messageId/timeline` | `{ messageId, timeline }`; events contain `channel`, `event`, and `at` |
| `GET /v1/messages/:messageId/trace` | Delivery summary and `waterfall` spans |
| `POST /v1/messages/templates/preview` | Preview inline template rendering |
| `POST /v1/receipts` | Submit a client receipt using `messageId`, `channel`, and `event` |
| `GET /v1/dlq` | Failed messages with `limit` and `offset` pagination |
| `POST /v1/dlq/replay` | Replay selected `messageIds` |
| `POST /v1/dlq/replay-mutated` | Replay with supported mutations or `dryRun: true` |
| `/v1/batches` | Create, inspect, pause, resume, or cancel batch contexts |
| `/v1/suppressions` | Manage suppression identifiers |
| `/v1/webhook-subscriptions` | Configure signed customer callbacks |
| `/v1/sandbox/messages` | Inspect or clear recent team sandbox records |

## Errors and health

Messaging validation errors use this shape (detail text depends on the validation failure):

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid message request",
    "details": [{ "path": "userId", "code": "invalid_type", "message": "Required" }]
  }
}
```

Other messaging errors include `IDEMPOTENCY_CONFLICT` (`409`), `NOT_FOUND` (`404`), and `SERVICE_UNAVAILABLE` (`503`, with `Retry-After`). Error envelopes differ in some other route families; inspect the HTTP status and response body. Delivery failures occur after acceptance and are visible through message status and events.

`GET /health` checks database and Redis connectivity plus readiness. `GET /health/readiness` returns `200` or `503`; `GET /health/liveness` returns a process liveness response. `GET /metrics` serves Prometheus metrics. These routes are outside `/v1`.
