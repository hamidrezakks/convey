# Convey System Architecture

Convey separates synchronous acceptance from asynchronous delivery. The supported qualification target is one regional deployment with PostgreSQL 18, a Redis-compatible store, server workers, the web console, and optional plugins. Local ARM64 tests do not establish AMD64 support, active-active correctness, geographic failover, or production throughput.

<Callout type="info" title="Acceptance is not delivery">
  A successful send returns HTTP 202 and an opaque `msg_<ULID>` message ID after durable acceptance. Provider calls, retries, receipt processing, and recipient delivery happen later. No public latency or availability SLA is implied.
</Callout>

## Fast-Path Ingestion

1. Authentication resolves the stored role, tenant, team, and sandbox scope. Request headers cannot elevate that identity.
2. A Redis-compatible `SET NX` reserves an idempotency key scoped to team and sandbox/production, with a canonical request hash.
3. A PostgreSQL transaction inserts the encrypted message and its outbox work.
4. The response records acceptance; workers process the durable work asynchronously.

The default idempotency retention is 24 hours. A completed identical request replays its saved response. A different payload or a request still processing returns a conflict. Expiration can permit new work under a reused key, and queue-store loss invalidates retained-key assumptions. Retries across a third-party network cannot guarantee exactly one delivery.

See [API reference](/docs/api-reference) for the full wire payload. The SDK shorthand `channel`, `recipient`, and `content` is normalized by the client into the API's `recipients` and `channels` arrays.

## Transactional Outbox

The default shard router computes a Murmur32v3 hash from `tenantId:messageId` across 16 virtual shards. The relay claims ready outbox rows using `FOR UPDATE SKIP LOCKED`, publishes deterministic jobs, then marks claimed rows processed after enqueueing. Expired claims are eligible for recovery.

```text
API acceptance -> PostgreSQL messages + outbox transaction
              -> outbox relay -> BullMQ jobs -> dispatch workers
              -> provider response / signed receipt -> later outcome
```

The outbox uses `state`, `available_at`, `locked_at`, and `processed_at` fields. `SKIP LOCKED` lets other pollers skip claimed rows; it does not remove database locking or prove loss-free operation under every store failure. Restore and replay need deployment-specific recovery procedures.

## PostgreSQL Storage & Retention

The canonical `messages` definition uses range partitioning on `created_at`. Maintenance manages partitions and retention, and time-bound queries can benefit from partition pruning. Partition creation and removal still require PostgreSQL locks and operational planning.

Before the first release, the repository edits canonical CREATE definitions instead of adding upgrade patches. A changed baseline requires explicitly fresh disposable stores. Once the first release is published, schema changes need a versioned migration ledger and tested upgrade paths. See [deployment](/docs/deployment) for operational boundaries.

## Zero-Trust Encryption

`PayloadEncryptionManager` uses AES-256-GCM, HKDF derivation, random IVs, authenticated ciphertext, key versioning, and a pluggable key-provider boundary. Provider credentials use separate encrypted storage. Production requires an operator-supplied payload key.

Authorized APIs and workers decrypt data when needed; plaintext is not confined exclusively to provider socket transport. The included mock KMS provider is a test implementation. Logical recipient revocation prevents permitted service reads but is not cryptographic erasure: HKDF keys remain derivable from a retained master key. Encryption alone does not certify regulatory compliance.

See [payload key management](https://github.com/hamidrezakks/convey/blob/main/docs/operations/payload-key-management.md) for configuration, rotation, and recovery.

## Fairness Scheduler

The repository includes priority queues and a Deficit Round Robin scheduler with configurable tenant weights. Scheduler tests exercise fairness under defined workloads. These tests do not guarantee a universal fairness index or exact delivery deadlines when capacity, providers, or tenant traffic differ.

Near-term execution within 30 minutes uses BullMQ. Longer schedules remain in PostgreSQL until promotion. Scheduling accepts future processing, not exact delivery at the requested time.

## Provider Routing, Retries & Receipts

Configured routes, health tracking, circuit breakers, and recovery ramps support dispatch decisions. Provider throttling and transient failures use bounded retries. A timeout can leave provider acceptance uncertain; automatic retry or intentional replay may produce another delivery and charge.

Webhook signature schemes and receipt types are vendor-specific. Customer event consumers must verify the exact signed bytes, deduplicate event IDs, and tolerate out-of-order events. Adapter listings are separate from certification; see [provider readiness](/docs/providers).

## WhatsApp Cost Optimization

Session conversion is optional and enabled in provider configuration. It requires a tracked inbound user reply, an active session, and available template body text. Eligible templates can then be rendered as text; otherwise the original template remains.

Savings metadata is a configured estimate. Actual eligibility, vendor fees, and invoice reconciliation require separate evidence. The landing calculator is illustrative and uses user-selected assumptions.

## Go Recipient Gateway

The [independent Go gateway](/docs/gateway) accepts a `userId`, verifies caller scope with Convey, resolves missing channel addresses through a customer resolver, and forwards the request to the existing service. Explicit recipient overrides take precedence. Native bulk lookup can coalesce concurrent requests.

Its customer HTTP adapter is a reference contract that must be adapted to the real customer service. The gateway has no database, Redis dependency, schema migrations, or cross-request customer cache. It does not add a transaction across customer lookup and downstream acceptance.
