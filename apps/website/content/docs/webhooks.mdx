# Webhooks

Customer webhooks deliver message and inbound events from Convey to your application. Provider webhooks travel in the other direction and use provider-specific validation. The [repository API reference](https://github.com/hamidrezakks/convey/blob/main/docs/api.md) documents both route families.

## Create a customer subscription

`POST /v1/webhook-subscriptions` uses your key's tenant and team. Destinations must use HTTPS on port 443 and resolve to public addresses; credentials, fragments, private addresses, and redirects are not supported.

```bash
curl http://localhost:3000/v1/webhook-subscriptions \
  -H "Authorization: Bearer $CONVEY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "url": "https://your-public-host.example/webhooks/convey",
    "events": ["message.sent", "message.delivered", "message.failed", "ping.test"]
  }'
```

Replace the destination with your application's public HTTPS URL. The response is `{ "success": true, "subscription": { ... } }`, including the generated signing `secret`. Store that secret securely. You can also supply your own `secret` in the request.

List subscriptions with `GET /v1/webhook-subscriptions` and delete one with `DELETE /v1/webhook-subscriptions/:id`. `POST /v1/webhook-subscriptions/:id/test` queues `ping.test` for matching subscriptions in the authenticated tenant/team. Include `ping.test` or `*` in the event filter to receive it; the current implementation does not limit that ping to the path's subscription ID.

## Actual event payload

The dispatcher sends this envelope:

```json
{
  "event": "message.delivered",
  "timestamp": "2026-10-10T12:00:01.000Z",
  "data": {
    "messageId": "msg_01J0N7C0W7X2R6S8V9Q9B1E4G3",
    "channel": "email",
    "status": "delivered",
    "timestamp": "2026-10-10T12:00:00.000Z"
  }
}
```

`event` identifies the event, the outer `timestamp` is the dispatch time, and `data` varies by event. Workers emit `message.sent`, receipt events such as `message.delivered`, `message.opened`, `message.read`, `message.failed`, and `message.bounced`, and `inbound.message_received`. Availability depends on the provider and receipt evidence. `message.sent` records provider acceptance, not recipient delivery.

The current envelope has no stable event ID. Handlers should tolerate duplicates and delayed or out-of-order receipts, using application state and the message/channel/event data to make repeated processing safe. The [dispatcher source](https://github.com/hamidrezakks/convey/blob/main/apps/server/src/queues/workers/customer-webhook-dispatch.worker.ts) defines the wire payload.

## Verify the signature before parsing

`X-Convey-Signature` has the format `t=<unix-seconds>,v1=<hex-hmac>`. Convey signs the exact UTF-8 body prefixed with the header timestamp and a period: `timestamp.rawBody`. The algorithm is HMAC-SHA256 using the subscription secret.

```typescript
import { verifyWebhookSignature } from '@convey/sdk';

type CustomerEvent = {
  event: string;
  timestamp: string;
  data: Record<string, unknown>;
};

export async function POST(request: Request): Promise<Response> {
  const signature = request.headers.get('x-convey-signature') ?? '';
  const rawBody = await request.text();
  const secret = process.env.CONVEY_WEBHOOK_SECRET!;

  if (!(await verifyWebhookSignature(rawBody, signature, secret, 300))) {
    return new Response('Invalid signature', { status: 401 });
  }

  const event = JSON.parse(rawBody) as CustomerEvent;
  // Validate the fields your application uses and persist/process safely.
  console.log(event.event, event.data.messageId);
  return Response.json({ received: true });
}
```

The helper checks timestamp drift with a 300-second tolerance. Preserve the original body before JSON middleware transforms it. SDK event constructors and framework routing adapters currently declare `id`/`type` fields that differ from the server's `event` envelope; this example uses the signature helper and explicit wire fields.

## Delivery and retries

Return a `2xx` response after accepting the event. The dispatcher uses a 10-second request timeout and retries network errors, `429`, and `5xx` responses with jitter, for up to three total attempts. Other non-`2xx` responses are recorded as failures without that transient retry. Retry timestamps and signatures are regenerated for each attempt.

## Inbound provider receipts

Configure upstream vendors to call `POST /v1/webhooks/:provider`. WhatsApp status and incoming endpoints also exist at `/v1/webhooks/:provider/status` and `/v1/webhooks/:provider/incoming`, with GET verification routes for supported handshakes. Provider-specific signatures, secrets, and supported events depend on the adapter. The customer `X-Convey-Signature` scheme does not verify vendor requests; check the [capability matrix](https://github.com/hamidrezakks/convey/blob/main/docs/operations/provider-capability-matrix.md) for evidence.
