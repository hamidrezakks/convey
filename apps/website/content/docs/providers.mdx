# Provider Catalog & Readiness

Convey includes adapter modules and catalog metadata for email, SMS, WhatsApp, push, chat, and tool transports. A catalog entry describes an integration boundary; it does not establish live delivery, vendor feature parity, measured latency, or current account health.

<Callout type="info" title="Twenty incomplete native adapters remain unavailable">
  Credentials, registry overrides, or administrative registration cannot enable an incomplete adapter. Seeding creates disabled entries and preserves existing credentials. Vendor-specific contract evidence is required before an adapter can leave the unavailable cohort.
</Callout>

## Readiness Evidence

Keep three kinds of information separate:

- **Adapter declarations:** Implemented request/response transformers and declared capability flags.
- **Offline contract coverage:** Fixtures exercising vendor URLs, authentication, payload encoding, response validation, errors, throttling, uncertain acceptance, and receipt behavior. The initial focused qualification covers Resend and Twilio, with broader transport suites retained.
- **Live certification:** Designated vendor accounts and approved recipients, observed delivery receipts, and pricing reconciled against vendor records. Mock fixtures do not satisfy this stage.

The [capability matrix](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/operations/provider-capability-matrix.md) and [porting audit](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/provider-porting-matrix.md) record declarations and implementation gaps. The [certification gates](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/operations/provider-certification.md) define what evidence is needed. `provider-certification-evidence.json` tracks vendor-specific evidence for removing an adapter from the unavailable cohort; generic adapter-shape tests do not meet that gate.

## Configuration

Platform administrators can use the web console or `POST /v1/admin/providers/register`. Tenant and sandbox keys cannot perform platform writes. Query `/v1/admin/providers/catalog` and `/v1/admin/providers/configured` for the deployment's entries rather than assuming the landing catalog is live state.

The examples below show registration request shapes for adapters present in the repository. Credentials are placeholders. **Costs are illustrative configured estimates, not vendor price quotes.** Production sends require an explicit validated provider price; `unitCost` and `baseCurrency` persist `config.pricing: { cost, currency }`. Estimates do not reconcile invoices.

Provider-specific credentials and required sender fields come from the adapter configuration types. These values are persisted and encrypted through the registration path; arbitrary environment variables alone do not register an account.

## Routing & Failure Handling

Primary selection, priorities, weights, and `fallbackProviderId` are provider configuration. The message contract supports channel-level `fallback.rules` and `cascade`; it does not accept the landing's former `routing.strategy` or `fallbackChain` payloads. See [API reference](/docs/api-reference) for the accepted shapes.

Retries are bounded and respect throttling. A network timeout is not proof the provider rejected a send. Delivery receipts and read events are provider-specific, and signed ingress needs each vendor's own scheme and correlation coverage. Customer event consumers must verify exact signed bytes, deduplicate event IDs, and tolerate out-of-order events.

## WhatsApp Session Conversion

Conversion is opt-in through provider configuration. The interceptor checks a tracked active session and requires template body text before converting a template to text. If those prerequisites are absent, the original template remains. Actual eligibility and fees must be verified with the provider; the repository's saved-cost metadata and landing calculator are estimates.

## Sandbox

Use a scoped sandbox credential or the SDK's supported sandbox request option to test acceptance without production provider calls. Sandbox scope is part of authentication and idempotency isolation, and it does not consume production budget. A simulated outcome is not a live provider receipt or a measured delivery success rate. See [configuration](/docs/configuration) and [SDKs](/docs/sdks).
