# Benchmark Evidence & Limits

Convey's most explicitly scoped qualification measurements are recorded in [v1-qualification-evidence.json](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/operations/v1-qualification-evidence.json), dated **2026-09-28**, for implementation commit `4a98ba2c3ce558ac98d02bbb5cff7c39d01f34e0`.

<Callout type="info" title="Local acceptance measurements">
  These runs used in-process `app.handle` requests, a local PostgreSQL 18 and Redis 7.4, Bun 1.4.2, and a macOS ARM64 host with mock providers. They exclude network/container latency and real vendor delivery. They do not establish a public latency SLA, sustained production capacity, or regional failover correctness.
</Callout>

## Recorded Qualification Results

Both profiles sent a single short email payload per request.

| Profile | Request count | Concurrency | Recorded duration | Acceptance p95 | Acceptance p99 | Maximum |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| Burst | 200 | 10 | Not recorded in this profile | 27.76 ms | 51.43 ms | 59.15 ms |
| Sustained, configured 50 requests/second | 1,000 | 5 | 20.525 s | 91.41 ms | 123.57 ms | 164.45 ms |

The configured qualification thresholds were p95 under 250 ms and p99 under 1,000 ms. Both recorded profiles passed those test gates. A test threshold is an internal qualification condition, not a customer SLA. The sustained run is short and does not establish a long-duration soak result.

HTTP 202 records durable acceptance. Provider transport, retries, subsequent receipts, and recipient delivery require separate measurement. Query later message outcomes or consume verified customer events; acceptance timing cannot stand in for delivery timing.

## Historical Micro-Engine Report

The repository's [historical benchmark report](https://github.com/hamidrezakks/convey/blob/a2daf909f9deb825a29cb571bf18b9c3efd94008/docs/benchmarks.md) includes isolated operations such as shard hashing, tracing, template rendering, encryption, and Redis reservations. The landing's micro-engine table reproduces selected values from that report.

These operation rates cannot be added together or treated as message-delivery capacity. The historical report lacks complete hardware, commit, fixture, and repeatability metadata, and its figures are not current qualification claims. Results for mocked webhook handling do not measure a live provider's receipt throughput.

The implementation in `apps/server/bench/bench-harness.ts` measures elapsed time with `performance.now()`, warms up each operation, records an array of durations, sorts it, and selects percentiles. It is not an HDR histogram implementation and does not establish nanosecond timing precision. Small sample counts and sub-millisecond rounding limit interpretation of the tail percentiles.

## Reproduce Locally

Prepare the database and Redis-compatible service as described in [quickstart](/docs/quickstart). Run commands from the repository root:

```bash
# Algorithm and storage-operation harness
bun run bench:engine

# API, pipeline, and stress harnesses
bun run bench:api
bun run bench:pipeline
bun run bench:stress
bun run bench:all

# Automated benchmark and stress test gates
bun run test:bench
bun run test:stress

# Explicitly scoped acceptance qualification profiles
bun run qualification:load
bun scripts/qualification/acceptance-load.ts --sustained
```

Some suites need prepared local stores and configured test fixtures. Running a benchmark can create test data; use disposable stores and follow each harness's setup. A test or harness name containing “planetary” does not establish geographic scale.

Record the tested commit, runtime versions, host architecture, fixture/provider mode, database state, payload size, concurrency, offered rate, duration, sample count, and output when sharing results. Use network and container paths plus sufficiently long runs to assess an intended deployment. Never infer a live delivery guarantee from offline acceptance fixtures.
